# ADR-020: Extensions, capabilities and repositories

## Decision

- **Extension** is the package: what is installed, versioned and enabled per workspace (an Agent SDK plugin folder plus an `extension.json` manifest). **Capability** is what an extension lets miyagi do, declared in its manifest (`provides`): run containers, publish a quiz in a Moodle classroom, read submissions. Skills say what miyagi knows how to do; capabilities, what it can do. The core asks for capabilities, never for an extension: the classroom operations of ADR-014 (`publish-quiz`, `submissions`…) are capabilities of a classroom extension.
- Kinds of extension: **domain** (skills, templates, reference knowledge, policies: FP Dual, competency assessment), **classroom** (a connector: Moodle, Google Classroom), **service** (an external API: YouTube, voice), **runtime** (running code: Docker, Git, Python).
- Extensions are **dependencies of the workspace**. `workspace.json`, shareable and versionable, holds the label, `classrooms[]` (each with `id`, `type`, its platform's fields), `groups[]` and `extensions` (name → version range, `"builtin"` for the ones shipped with miyagi). Secrets live in `.env`, never in `workspace.json`. `extensions.lock` pins each one: repository, exact version, commit and SHA-256.
- Installed extensions live in an immutable store, `~/.miyagi/extensions/<repo>/<name>/<version>/`, out of the agent's reach, verified against the lock when installed and when loaded. A workspace's own extensions, unpublished, live in its `extensions/` folder and are versioned with it.
- **Repositories.** The official one is `falkenslab/miyagi-extensions`: one folder per extension, tags `<name>@<x.y.z>`, a GitHub release per version with its tarball and SHA-256, and an `index.json` generated by its CI. Any repository with the same layout can be added by the user (`miyagi extension repo add <url>`); its extensions are named `<repo>/<name>`. There is no community catalog and no hub for resources.

## Motivation

Not every teacher needs the same miyagi: an FP computing teacher needs containers and Git, a secondary teacher a competency-assessment template. A small core that specialises through extensions avoids an agent with everything for everyone. Separating the package from the capability lets two extensions provide the same capability (Moodle and Classroom both give `submissions`) and lets the core stay platform-free. Treating extensions as dependencies makes a workspace reproducible on another computer and shareable within a department. One official repository is enough while falkenslab writes the extensions; the same format lets a school or a teacher add their own without a hub to moderate.

Rejected: `capability` as the package name (it collides with the classroom operations and mixes what is installed with what it enables); a `node_modules`-like copy per workspace (duplicates, and puts code next to what the agent reads and writes); npm as the registry (accounts, install scripts); a public catalog or resource hub (moderation and liability with no one to carry them).

## Consequences

- **Official** extensions install after showing what they declare. **Non-official** ones (from a repository the user added, or a workspace's own) need the repository added by hand, after an explicit warning that falkenslab hasn't reviewed it and that its code runs on the teacher's computer with their permissions; each extension is confirmed with what it declares (tools, network, student data, publishing, running code) and again when a version changes it.
- Non-official extensions may run code on the host, a shell included, once the user accepts that warning: this amends ADR-003 for them. The official runtime extensions run code in containers (the practice runner's model), never as a shell for the main agent.
- Whatever the source, the core keeps: the approval of what students see (ADR-008), every MCP tool treated as publishing unless confirmed read-only, no publishing in autonomous mode by a non-official extension unless enabled for it, secrets passed only to the extension that declares them and a clean environment for its processes, nothing about individual students in the knowledge base (ADR-005), and no extension text or tool result overriding the core's rules.
- A skill may require a capability (`requires` in its frontmatter) and is only offered when an enabled extension provides it: `practice-testing` only with `run-containers`.
- Versions are SemVer; `extension.json` states the `miyagiApi` it supports, and an incompatible extension isn't loaded. `miyagi extension add|remove|install|update|outdated|list|prune` and `miyagi extension repo add|remove|list`; `install` follows the lock, `update` stays within the range, a major version always asks again. Missing dependencies are reported and offered, never installed silently.
- To the teacher, miyagi speaks of capabilities (`/capabilities`, "for this you need the docker extension"); extensions are the technical word.
- `config.json` is migrated to `workspace.json` plus `.env`.
- Supersedes ADR-014 on packaging (manifest `extension.json`, not `miyagi.json`; one repository with every official extension, not one per extension) and ADR-016 on the catalog and the limits of third-party extensions (trust tiers, community review, runtime only in containers). Their guarantees that aren't listed here as changed still hold.
- Delivered by the features `extensions` (content level, Moodle built in, workspace dependencies) and `extension-repositories` (code level, repositories, the official repository).
