# Designing an activity, not just picking its type

`course-design` decides *which* activity type fits a given point in the course, and
warns against defaulting to the same one every time. This skill is the next step: once a
type has been chosen, design that specific activity well — its mechanics, not just its
name and instructions (`content-authoring` covers the generic writing/creation
mechanics that apply regardless of type). `quiz-design` already covers this same job for
quizzes specifically; use it for those instead of this skill.

Setting the designed activity up in Moodle is `assignment-building` (any assignment) or
`activity-building` (workshop, lesson, glossary, wiki, database, choice, feedback, forum
variants, H5P, book, plus completion, restrictions, badges and groups).

## Assignment

A good assignment prompt requires genuine reasoning, application, or production — not
something answerable by restating the course material. State clearly what evidence of
understanding the submission needs to show, not just a topic to write about. If it allows
file upload, say what format and roughly what's expected (length, structure) so the
grading criteria (`rubric-design`) has something concrete to check against.

## Forum (as a graded/structured activity, not general facilitation)

Design the opening prompt so it invites more than a one-line reaction: pose a question
with more than one reasonable position, or ask students to apply a concept to a case
rather than just share an opinion. If participation itself is graded, state the expected
minimum explicitly (e.g. one original post and one reply) instead of leaving it implicit.
Managing an already-running forum day to day is `forum-facilitation`'s job, not this
skill's.

## Workshop

Two phases, and both need real design: the **submission** phase needs a prompt as
concrete as an assignment's; the **peer-assessment** phase needs its own criteria (via
`rubric-design`) so students aren't just guessing what to look for in a peer's work. Set a
realistic number of submissions each student must assess — too few defeats the exercise,
too many turns it into busywork.

## Lesson

Design the branching deliberately: a wrong answer to a checkpoint question should route
to a page that actually addresses the misconception, not just "try again" or a page
identical to what a correct answer would show. A lesson with no real branches is just a
page with extra clicks — if that's all that's needed, use a page instead.

## Collaborative activities (wiki, glossary, database)

Build in individual accountability: without it, a shared collaborative activity tends to
concentrate on whoever contributes first, with everyone else free-riding. A clear
division of what each student/group is responsible for (a wiki section, a set of glossary
terms) makes the contribution traceable and gradable, even in a nominally collaborative
space.

## Reflection and feedback activities (survey/feedback module)

A genuine reflection prompt asks something specific enough to require an honest, thought-
out answer ("what was the hardest part of this topic and why", not "how did you find this
topic"). Avoid administrative-sounding filler questions that don't actually inform
anything — each question should have a clear reason for being asked.

## Choice

A real decision, not just there for its own sake: what the choice is *for* (grouping
students, gauging preference before scheduling something) should be clear from the
prompt.

## Using this alongside other skills

Once the activity's mechanics are settled here, `content-authoring` writes and creates it
in Moodle (name, instructions, accessibility), `rubric-design` builds its grading
criteria if it's evaluable, and `content-editor` reviews the final wording before
publishing.
